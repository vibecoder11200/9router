9Router Docs
前往应用

智能路由 & 自动回退

9Router 通过 3 层回退系统,自动将你的请求路由到最佳可用提供商。绝不再因配额限制或速率限制而中断编码。

工作原理

9Router 使用智能路由,最大化已有订阅价值、最小化成本,并保障 24/7 可用:

请求 → 9Router → 检查第 1 层 (订阅)
                     ↓ 配额耗尽
                     检查第 2 层 (低价)
                     ↓ 预算上限
                     检查第 3 层 (免费)
                     ↓
                     响应

3 层回退系统

第 1 层:订阅(主力)

  • Claude Code(Pro/Max)
  • OpenAI Codex(Plus/Pro)
  • GitHub Copilot
  • Antigravity(Google, FREE)

目标:充分挖掘你已付费订阅的价值。

第 2 层:低价(备用)

  • GLM-4.7(输入每 1M $0.60)
  • MiniMax M2.1(输入每 1M $0.20)
  • Kimi K2($9/月固定)

目标:订阅配额用完后的超低价备用(比 ChatGPT API 便宜 ~90%)。

第 3 层:免费(应急)

  • Kiro(6 个模型, Claude 免费)
  • OpenCode Free(无需登录)
  • Vertex AI($300 免费额度)

目标:零成本回退,实现无限编码。

自动切换

9Router 实时监控配额,自动切换提供商:

场景 1:订阅配额耗尽

用户请求 → cc/claude-opus-5
           ↓ 配额耗尽(达到 5 小时限制)
           自动切换 → glm/glm-4.7
           ↓ 每日配额耗尽
           自动切换 → minimax/MiniMax-M2.1
           ↓ 5 小时配额耗尽
           自动切换 → kr/claude-sonnet-4.5 (免费)
           ↓
           响应已送达 ✅

结果:零停机,无缝体验。

场景 2:速率限制

用户请求 → cx/gpt-5.6-sol
           ↓ 速率受限(请求过多)
           自动切换 → glm/glm-4.7
           ↓
           响应已送达 ✅

场景 3:提供商不可用

用户请求 → cc/claude-opus-5
           ↓ 提供商错误(503)
           自动切换 → 下一个可用模型
           ↓
           响应已送达 ✅

模型选择逻辑

9Router 基于以下因素选择最佳模型:

  1. 配额可用性 - 检查提供商是否仍有剩余配额
  2. 成本层级 - 优先订阅 → 低价 → 免费
  3. 重置时间 - 考虑配额何时重置
  4. 提供商健康度 - 跳过有错误的提供商；故障账号还受熔断器保护，冷却期内跳过、回归轮换前被动探活

优先级示例

对 cc/claude-opus-5 的请求:

1. 检查 Claude Code 配额
   ✅ 可用 → 使用 cc/claude-opus-5
   ❌ 耗尽 → 继续步骤 2

2. 检查回退层(若已配置)
   ✅ GLM 配额可用 → 使用 glm/glm-4.7
   ❌ 耗尽 → 继续步骤 3

3. 检查免费层
   ✅ Kiro 可用 → 使用 kr/claude-sonnet-4.5
   ❌ 全部耗尽 → 返回配额错误

配置选项

仪表盘设置

1. 启用/禁用自动回退

仪表盘 → 设置 → 智能路由
→ 切换 "Auto Fallback" ON/OFF
  • ON(默认):自动层级切换
  • OFF:严格模式,主模型不可用时返回错误

2. 设置预算上限

仪表盘 → 设置 → 预算控制
→ 每日上限: $5
→ 每月上限: $50

预算耗尽时,9Router 自动切换到免费层。

3. 配置回退顺序

仪表盘 → 设置 → 回退优先级
→ 拖动以重新排序每层内的提供商

自定义顺序示例:

第 1 层: Antigravity → Claude Code → Codex
第 2 层: MiniMax → GLM → Kimi
第 3 层: Kiro → OpenCode Free → Vertex AI

4. 配额重置通知

Dashboard → Alerts
→ Telegram / Discord / Webhook 渠道
→ 启用 "quota-near-limit" 事件

渠道设置与完整事件目录见告警。

最佳实践

1. 最大化订阅价值

策略:
- 将订阅模型设为第 1 层
- 在仪表盘监控配额使用
- 仅在订阅耗尽时使用低价层

示例组合:

cc/claude-opus-5 → glm/glm-4.7 → kr/claude-sonnet-4.5

2. 成本优化

策略:
- 先用 Antigravity 免费层(Google 账户)
- 回退到 GLM/MiniMax(超低价)
- 应急: Kiro(免费)

示例组合:

ag/gemini-3-flash → glm/glm-4.7 → kr/claude-sonnet-4.5

3. 质量优先

策略:
- 使用最佳模型(Claude Opus 5、GPT-5.6 Sol)
- 回退到优秀的低价模型(GLM-4.7)
- 最后手段: 免费层

示例组合:

cc/claude-opus-5 → cx/gpt-5.6-sol → glm/glm-4.7

4. 24/7 可用性

策略:
- 回退链中总是包含免费层
- 监控配额重置时间
- 在多个提供商间分散使用

示例组合:

cc/claude-opus-5 → glm/glm-4.7 → minimax/MiniMax-M2.1 → kr/claude-sonnet-4.5

结果:永不耗尽配额,随时编码。

  Claude Code: 剩余 2.5h / 5h (50%)
  Antigravity: 今日 450 / 1000 次请求
  GLM-4.7: 5M / 10M tokens (8h 后重置)

Dashboard → Alerts(Telegram / Discord / Webhook):

  ⚠️ quota-near-limit: Claude Code 已用 80%(1 小时后重置)
  🔴 all-accounts-locked: glm 所有账号被限流
  🔴 breaker-open: cx/gpt-5.6-sol 故障 —— 跳过 60 秒

渠道与按事件开关在告警页面配置。

使用分析

仪表盘 → 分析:
  今日: 50M tokens
    - 30M 通过 Claude Code(订阅)
    - 15M 通过 GLM-4.7($9)—— 其中 6M 为缓存(估算节省约 $3.60)
    - 5M 通过 Kiro(免费)
  
  成本: $9(对比 ChatGPT API $1000)
  节省: 99%

使用页面还按 provider/model 细分缓存 token 与估算节省 —— 见配额追踪。

故障排除

问题:"All providers quota exhausted"

方案:

  1. 查看仪表盘配额跟踪
  2. 等待配额重置(查看倒计时)
  3. 在回退链中加入免费层
  4. 或提高预算上限

问题:"Too many fallback switches"

方案:

  1. 检查主提供商是否宕机
  2. 提高配额上限(升级订阅)
  3. 使用更便宜的主模型(用 GLM 代替 Claude)

问题:"Unexpected costs"

方案:

  1. 仪表盘 → 分析 → 查看使用情况
  2. 设置每日/每月预算上限
  3. 非关键任务切换到免费层
  4. 使用带免费回退的组合
